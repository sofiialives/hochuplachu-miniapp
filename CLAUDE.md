# hochuplachu-frontend

## Purpose
Angular 21.2.12 zoneless клиент для проекта «Хочу плачу». Веб-приложение и Telegram Mini App: карты (каталог, выпуск, пополнение), eSIM (мои eSIM + каталог тарифов с фасетами), сервисы (Steam-пополнение, гифткарты), оплата (методы из `/payment/methods`: Coincat-валюты и/или СБП через kassaai/platega/enot — управляются админ-разделом «Методы оплаты»), история транзакций, заказы всех типов, профиль, реф-программа, admin-панель. Дизайн-язык — визуальный язык лендинга hochuplachu-landing (жёлтый primary #FED136, тёмный on-primary #3D2000, шрифты Unbounded/Onest, мягкие тени, CSS-анимации) — см. `DESIGN.md`, раздел «Visual Language v2». Производные оттенки считаются через `color-mix()` от `--color-primary`, поэтому CatCard (та же сборка, свой brand.json с primary `#d2aa22`) автоматически получает свои hover/soft/градиенты.

## Разделы и навигация
- bottom-nav — 5 пунктов: Главная `/`, Карты `/cards`, eSIM `/esim`, Сервисы `/services`, Профиль `/profile` (гостю пункт «Профиль» ведёт на `/login`). Активный пункт — залитая брендовая пилюля (градиент primary + on-primary текст).
- `/` — главная-агрегатор: hero карт (авторизованному с картами — компакт-виджет + статус «Карта выпускается…»), реф-баннер, секция eSIM (топ-4 тарифа), секция Сервисы (featured + сетка). coming_soon-разделы — заглушка «Раздел в разработке» (`GET /catalog/sections`).
- `/cards` — бывший авторизованный режим главной: карусель карт, детали, Пополнить/Выпустить; гостю — каталог. `/cards/new` (под authGuard) — выбор карты к выпуску.
- `/esim` — Мои eSIM (статус, прогресс трафика, QR-диалог, «Продлить», usage-refresh) + каталог с фасетами страна/дни/объём (bottom-sheet). Чекауты: `/esim/:id/checkout`, `/esim/my/:esimId/recharge` — БЕЗ authGuard (гостевой email-flow внутри страницы; authGuard терял бы query). Страница заказа: `/esim/orders/:id`.
- `/services`, `/services/:slug` (gift_card: сетка номиналов; account_topup: логин+сумма+пресеты+«К зачислению»), `/services/:slug/checkout?login=&amount=|denomination=` — тоже без authGuard. Страница заказа: `/services/orders/:id`.
- payment.page — ОДИН компонент для всех типов оплат, дискриминация по route `data:{orderKind}`: `card` (`/orders/:id/payment`), `topup`, `renewal`, `esim` (`/esim/orders/:esimOrderId/payment`), `esim_recharge` (`/esim/recharges/:esimRechargeId/payment`), `service` (`/services/orders/:serviceOrderId/payment`). Для eSIM/gift_card поллинг идёт до ТЕРМИНАЛЬНОГО статуса (не isPaid); с терминального экрана — переход на страницу заказа. `goHome()` ведёт по типу: карты → `/cards`, eSIM → `/esim`, сервисы → `/services`.
- `/profile` + `/profile/orders` (история заказов всех типов), `/history` — история транзакций карт (вход со страницы Карт).

## Tech Stack
- Angular 21.2.12 (standalone, signals, новый control-flow `@if/@for`, zoneless via `provideZonelessChangeDetection`).
- Раздача — nginx из `dist/hochuplachu-frontend/browser/`. SPA-fallback на `index.html` живёт в [nginx.conf](nginx.conf).
- `@jsverse/transloco` для i18n (RU/EN, RU дефолт).
- `@telegram-apps/sdk` (через `window.Telegram.WebApp`) для Mini App.
- `angularx-qrcode` для QR-кодов.
- Sass-токены в `src/styles/_tokens.scss` (палитра лендинга + производные через `color-mix()`); 8 брендируемых runtime-цветов переопределяются через `window.__APP_CONFIG__.brand.colors`.
- Шрифты self-hosted: `public/fonts/*.woff2` (Onest 400/500/700, Unbounded 700 — копии из hochuplachu-landing), `@font-face` прямо в `global.scss` (angular.json styles содержит только его). Google-fonts ссылок в index.html больше нет; display-шрифт preload'ится.
- Предзагрузка разделов: `withPreloading(SectionPreloadStrategy)` — чанки пунктов bottom-nav догружаются в фоне после первой навигации (см. Team Notes «Фоновая предзагрузка разделов»).
- Анимации — только CSS (без `@angular/animations`, пакет deprecated в v21): `withViewTransitions()` в провайдере роутера + `::view-transition-*` в global.scss (fade+slide 180–260 мс), глобальная утилита `.stagger-in` (каскадное появление карточек каталогов), spring-easing (`--ease-spring`) для диалогов/bottom-sheet/тостов, hover-lift карточек. `prefers-reduced-motion: reduce` глобально отключает движение.
  Два правила перехода, без которых он читается как мигание: (1) **прозрачность анимирует только УХОДЯЩИЙ кадр**, и он лежит поверх приходящего (`z-index: 1`) — когда её анимировали оба, в середине перехода оба слоя были полупрозрачны, сквозь них просвечивал фон и получалась вспышка; приходящий только выезжает. (2) **Футер-меню вынуто из перехода** собственным `view-transition-name: bottom-nav` (задаётся в `bottom-nav.component.ts`, правила — в global.scss: группа без анимации, старый снимок `display:none`): как `position: fixed`-элемент без своего имени оно попадало в снимок `root` и на каждом переключении вкладки уезжало и кросс-фейдилось вместе со страницей, хотя само не меняется. Любому новому фиксированному элементу поверх страницы нужно то же самое.

## Commands
- `npm install` — установка зависимостей (требует доступа в npm-registry).
- `npm start` — dev-сервер `ng serve` на `:4200`. Перед стартом запускается `brand:sync` (см. ниже).
- `npm run build` — production-build в `dist/hochuplachu-frontend/browser/`. Тоже триггерит `brand:sync`.
- `npm run brand:sync` — `scripts/sync-brand-config.mjs`: читает `BRAND_CONFIG_URL` из `.env`, скачивает brand.json + лого, генерит `public/assets/runtime-config.js` (паритет с docker-entrypoint).
- `npm test` — Karma + Jasmine.

## Configuration (runtime)
Через `window.__APP_CONFIG__`, который инжектируется `public/assets/runtime-config.js`. В Docker-образе скрипт перезаписывается `docker-entrypoint.sh`:

| ENV | Что задаёт |
|---|---|
| `BRAND_CONFIG_URL` | **Обязательный** источник brand.json. Принимает http(s) URL или локальный путь (опционально с префиксом `file://`). Тот же источник читает backend. |
| `API_BASE_URL` | Точка входа backend (`/api/v1` или абсолютная) |
| `CHATWOOT_HOST` | Домен НАШЕГО чат-прокси cc-gochatwoot для web-чата поддержки (например `https://chat.hochuplachu.com`) — с него грузится `widget.js`. Пусто = чат выключен. |

### Brand JSON
Один JSON, две точки чтения (frontend + backend). Структура — в `coincat/brand-config.example.json`. На старте контейнер:
1. Берёт `BRAND_CONFIG_URL` — `curl` для http(s) или `cp` для локального пути — кладёт в `assets/brand.json`.
2. Тем же способом тянет `logo_url` в `assets/logo.png`.
3. Тянет `favicon_url` (или `logo_url` как fallback) в `assets/favicon.{ext}`; `RuntimeConfigService.applyFavicon()` на клиенте подменяет `<link rel="icon">` в head.
4. Встраивает весь brand-объект в `assets/runtime-config.js` под ключом `window.__APP_CONFIG__.brand`.

`runtime-config.js` подключён синхронным `<script>` в `<head>` — до парсинга `<body>`. Его inline-bootstrap ставит CSS-переменные `--color-*` и `--brand-logo: url(...)` прямо на `<html>`, чтобы splash (см. ниже) сразу красился в брендовые цвета без вспышки defaults.

Цвета применяются как `--color-*` CSS-переменные через `RuntimeConfigService.applyThemeFromConfig()` (fallback для dev / случаев, когда inline-bootstrap не отработал — он сам ставит `data-favicon-applied=1` и сервис делает no-op). Ключи в JSON — snake_case (`primary`, `on_primary`, `surface_card`) преобразуются в kebab-case CSS-переменные (`--color-primary`, `--color-on-primary`, `--color-surface-card`).

### Splash screen
До bootstrap'а Angular пользователь видит inline-splash из `src/index.html`: фон `--color-canvas`, центрированный лого 112×112 с `opacity: .35` (background-image из CSS-переменной `--brand-logo`), под лого — спиннер с `border-top-color: --color-primary`. Никакой загрузки шрифтов / бандлов не требуется — стили инлайн, цвета и лого приходят из `runtime-config.js` синхронным `<script>` в `<head>`.

`AppComponent.hideSplash()` слушает первый `NavigationEnd` (`take(1)`), ставит класс `.app-ready` на `<html>` → CSS-правило `opacity: 0` → элемент удаляется по `transitionend` (фолбэк через `setTimeout(800)`). К этому моменту `provideAppInitializer` (auth.bootstrap + loadPaymentInfo) уже завершён и первая страница отрисована.

## Авторизация (поток)
1. `AppComponent.ngOnInit` вызывает `AuthService.bootstrap()`.
2. `bootstrap()` читает `window.Telegram.WebApp.initData` → если есть, кладёт в signal `initData` (interceptor добавит заголовок). Иначе берёт bearer из `localStorage.hp.token`.
3. Дергает `GET /auth/me` — если 401, остаётся «гостем»; иначе устанавливает `user`.
4. `authGuard` (CanMatchFn) ждёт `bootstrap()` и редиректит на `/login` если нет user.
5. `appShell` после загрузки списка карт вызывает `EmailLinkDialog` если у TG-юзера нет email и есть карты.
6. Web-вход по email аккаунта с привязанным Telegram: `/auth/email/verify` возвращает `telegram_confirm: true` + `approval_token` вместо токена — страница показывает спиннер «Подтвердите вход в Telegram» и поллит `POST /auth/email/approval/poll` каждые 2 сек (`AuthService.pollApproval`), пока владелец не нажмёт «Разрешить»/«Отклонить» в боте (обрабатывается в `email-verify.page.ts` и в email-шаге `verification.page.ts`).
7. Обратное направление — «вход по email» изнутри Mini App: у TG-аккаунта без `email_linked` на странице профиля (под шапкой аватар/имя/email) показывается кнопка «Войти по email» → `EmailLinkDialog` в `mode="login"` (closable). Реального login-flow тут нет (middleware backend'а всегда предпочитает `X-Telegram-Init-Data` bearer'у) — это link-flow: backend поглощает существующий email-аккаунт вместе с картами/заявками (merge), после `linked` профиль закрывает диалог и освежает глобальный кэш карт (`onEmailLinked` в profile.page.ts).

## Mini App startapp (параметры в `t.me/<bot>?startapp=...`)
Telegram пропускает в `startapp` только `[A-Za-z0-9_-]` и ≤64 символа, поэтому querystring туда не помещается. Договорённость с backend:

| Символ | Значение |
|---|---|
| `-`  | разделитель `key`/`value` (вместо `=`) |
| `--` | разделитель пар (вместо `&`) |

Парсер: [src/app/core/auth/start-param.ts](src/app/core/auth/start-param.ts). Backend-зеркало: [internal/utils/startparam.go](../goprojects/src/bitbucket.org/biomax1251/cc-bitrex-hochuplachu/internal/utils/startparam.go) — при изменении формата правьте оба файла одновременно.

Примеры:
- `?startapp=ABC123` → `{ ref: "ABC123" }` — legacy, одиночный токен без дефиса считается голым реф-кодом. Так работают существующие шеринг-ссылки рефовода (см. `internal/controllers/referral.go`).
- `?startapp=ref-ABC--utm_source-telegram--utm_campaign-spring` → `{ ref: "ABC", utm_source: "telegram", utm_campaign: "spring" }`.

После валидного `initData` `AuthService.consumeStartParam()`:
1. Если есть `ref` — `storeRef(ref)` (тот же `hp.ref` в localStorage, что и при web-заходе `/r/:refCode`; реф-ссылка рефовода ведёт на лендинг, который раздваивает поток: Telegram → `startapp=ref-{code}`, «В браузере» → `{web_base_url}/r/{code}`). Backend в `FindOrCreateByTelegram` независимо разбирает `payload.StartParam` и привязывает рефовода **по HMAC-валидированному значению** — то есть критичный для биллинга путь не полагается на этот localStorage.
2. `utm_*` ключи → `AnalyticsService.mergeUtm()` → `hp.utm_first_touch` (записывается один раз) и `hp.utm_last` (перетирается каждый заход). Те же ключи пишет URL-парсер UTM (`captureUtm` из query-string web-захода) — обе точки входа сходятся в один localStorage.

   Атрибуция кампании из этих меток разведена по трём каналам:
   - **Клиентский Matomo** — `AnalyticsService.captureTelegramUtm()` читает `start_param` синхронно на старте (до `trackPageView`), а `applyMatomoCampaign()` в `loadMatomo()` выставляет кампанию в `_paq` через `setCampaignNameKey`/`setCampaignKeywordKey` + `setCustomUrl` (восстановленный `?utm_*` URL, т.к. в Mini App меток в URL нет) + `setCustomVariable` слоты 5/6 (source/medium) — зеркало серверных cvar. Берётся first-touch. Порядок критичен: кампания ставится ДО `trackPageView`, иначе pageview уходит без источника.
   - **Серверный Matomo** — backend при реальном `paid` шлёт ecommerce-конверсию с `_rcn`(utm_campaign)/`_rck`(utm_term) + cvar 5/6 (`analytics_client.go`), метки берёт из `User.UTMFirstTouch` (их фронт кладёт в тело `/orders/issue` через `getUtm()`).
   - **Yandex.Метрика** — кампанию из start_param НЕ несёт (в неё UTM не прокидываются); Метрика видит источник только на прямом web-заходе, где метки есть в реальном URL.

Тот же ULID backend шлёт как `uid` в серверной Matomo-конверсии — совпадение uid с обеих сторон и есть склейка; формат uid менять только синхронно с `analytics_client.go`. `extend-service.page` шлёт `matomo_cid`/`utm` как checkout/topup (backend теперь трекает goal `renewal_paid`). Деплой backend-first.
